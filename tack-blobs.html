§ 01 / Problem

IPFS pins everything forever.
Your pipeline doesn't need forever.

Agentic workflows generate intermediate state that needs to be verifiable — but only for the duration of a job. Permanent storage is the wrong primitive for ephemeral data.

Today · IPFS pins

Permanent. Slow. Overbuilt.

IPFS pinning is designed for content you want to keep. Minimum pricing floors, 30-second propagation, and no native TTL make it a poor fit for inter-agent handoffs that live for 5 minutes. You're paying for permanence you don't need.

Tack Blobs · New

Ephemeral. Fast. Verifiable.

EIP-4844 blobs post in under a second, auto-expire via TTL, and leave a KZG commitment on-chain permanently — so agents can verify provenance long after the data is gone. Pay per blob in USDC. No recurring charges.

§ 02 / The loop

Five steps. One signature.

The same x402 payment flow you know from Tack pins — applied to blobs with TTL.

1

POST payload

Agent sends data to /blobs with TTL header set

2

402 returned

Tack returns price based on size × duration

3

Sign payment

One on-chain USDC transfer via x402 or MPP

4

202 + blob ID

Tack posts to EIP-4844. KZG commitment stored on-chain

5

Auto-expire

Data pruned at TTL. Commitment proof remains forever

⚡ Batch mode
6 blobs. One signature.

POST up to 6 blobs in a single transaction via /blobs/batch — packing up to ~768KB into one x402 payment signature. Ideal for multi-step pipeline flushes, embedding batches, or parallel agent outputs that need to land atomically.

→ Single USDC payment for the batch
→ One KZG commitment per blob
→ Independent TTLs per blob in batch

§ 03 / Use cases

What your agents actually need
to pass around.

Blobs are ideal for structured, small, high-frequency payloads. Under 128KB, high verifiability requirement, short shelf life.

🔁

Inter-agent handoffs

Agent A pins a task result as a blob. Agent B retrieves by blob ID, verifies the KZG proof, and continues the pipeline. The data is gone in 10 minutes. The proof lives forever.

Typical size 2–20KB
⚡

Tool call caching

Expensive deterministic operations — web scrapes, API calls, complex computations — get posted as a blob. Any agent in the fleet can verify and reuse the result without re-executing. Blob expires when the cache window closes.

Typical size 1–50KB
🧠

Session state snapshots

Checkpoint running agent memory mid-pipeline. Embeddings, context windows, intermediate reasoning — serialized and posted. Retrievable by any agent in the same job, gone when the session ends.

Typical size 10–100KB
📄

RAG query receipts

Not the corpus — the retrieved chunks used to generate a specific response. Post them as a blob so any downstream system can audit exactly what context the agent had when it made a decision.

Typical size 5–30KB
🧾

Verifiable task receipts

On-chain payment, off-chain result. Post the output as a blob, keep the KZG commitment as permanent proof of delivery. The receipt is verifiable long after the data expires.

Typical size <5KB
🔗

Inference input batches

Pass prompt batches, embedding sets, or structured API responses between pipeline steps. Blob IDs as pointers replace in-memory passing — decoupled, verifiable, and chain-agnostic.

Typical size 20–128KB

// Post a blob with 30-minute TTL · x402 on Taiko or Base
import { wrapFetchWithPaymentFromConfig } from "@x402/fetch";
import { ExactEvmScheme, toClientEvmSigner } from "@x402/evm";
import { privateKeyToAccount } from "viem/accounts";
import { createPublicClient, http } from "viem";
import { taiko } from "viem/chains";

const account = privateKeyToAccount("0x...");
const signer  = toClientEvmSigner(account, createPublicClient({
  chain: taiko, transport: http()
}));

const pay = wrapFetchWithPaymentFromConfig(fetch, {
  schemes: [{ network: "eip155:167000", client: new ExactEvmScheme(signer) }]
});

// Serialize your payload — anything under 128KB
const payload = JSON.stringify({
  task_id: "job-abc123",
  result: embeddingVector,
  agent: "retriever-v2",
  timestamp: Date.now()
});

// POST to /blobs with TTL — 402 → sign → 202
const res = await pay("https://tack.inferenceroom.ai/blobs", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "X-Blob-TTL-Minutes": "30",       // 5 to 25920 (18 days)
    "X-Blob-Tag": "handoff:retriever→ranker" // optional label
  },
  body: payload
});

const { blob_id, commitment, expires_at } = await res.json();

// blob_id  → pass to downstream agent
// commitment → KZG proof, stored on-chain permanently
// expires_at → Unix timestamp when data is pruned

// Verify a blob's KZG commitment on-chain
// The commitment is permanent — verifiable even after data expires
import { createPublicClient, http } from "viem";
import { taiko } from "viem/chains";

const client = createPublicClient({ chain: taiko, transport: http() });

// Given a blob_id from a previous handoff
const blob_id = "0x1a2b3c...";

// Fetch commitment from Tack (free, public)
const res = await fetch(
  `https://tack.inferenceroom.ai/blobs/${blob_id}/commitment`
);
const { commitment, tx_hash, posted_at } = await res.json();

// Verify commitment exists on-chain
const receipt = await client.getTransactionReceipt({ hash: tx_hash });

// If data is still within TTL, retrieve it
const data = await fetch(
  `https://tack.inferenceroom.ai/blobs/${blob_id}`
);

Blob pricing formula
price = clamp( sizeKB × $0.002 × days, $0.001, $10 )
Examples: 10KB for 30 min = $0.001 (floor) · 50KB for 1 hour = $0.001 (floor) · 100KB for 1 day = $0.20 · 128KB for 18 days = $4.61
Settlement rounds up to next USDC unit. Floor ensures every blob is economically viable to settle on-chain regardless of size or duration.
§ 07 / API

Standard endpoints. Familiar pattern.

Blobs extend the Tack API. Same base URL, same auth model, same payment flow. New routes prefixed at /blobs.

POST /blobs Post payload. Returns 402 with price → sign → 202 with blob_id + commitment x402 · MPP
GET /blobs/:blob_id Retrieve blob data within TTL. Returns 410 Gone after expiry public
GET /blobs/:blob_id/commitment KZG commitment + tx_hash + metadata. Always available, even after expiry public
GET /blobs List all blobs your wallet owns, including expired with commitments bearer
POST /blobs/batch Post up to 6 blobs in one tx (~768KB total). Single payment signature x402 · MPP
DEL /blobs/:blob_id Early-expire a blob your wallet owns. Commitment and proof remain bearer
GET /.well-known/agent.json A2A agent card — blobs capability included. Machines discover and verify public
