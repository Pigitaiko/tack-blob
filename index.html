Sub-month IPFS pinning
for agent pipelines. Auto-expiring. Receipt-preserved. x402-paid.

Agents need to pass payloads between steps. Today Tack pins last 1–24 months — overkill for a 10-minute handoff. Tack Short adds an optional ttl_seconds field so a pin can live anywhere from 5 minutes to 30 days, then auto-expire. The pin record is preserved as a permanent receipt; the gateway returns 410 Gone once the data is unpinned. Same x402 payment rails. No accounts. No API keys.

§ 01 / Problem

Tack pins last 1–24 months.
Your pipeline runs for minutes.

Agentic workflows generate intermediate state that needs to outlive the current step but not much longer. The current minimum-month duration is the wrong granularity for inter-agent handoffs.

Today · Tack pins

Month-floor. Manual cleanup.

Tack's existing pin lifetimes are designed for content you want to keep. An agent that pins a 2 KB tool-call result has to either let it sit for 30+ days or remember to call DELETE /pins/:id later. That's bookkeeping the agent shouldn't be doing.

Tack Short · New

5 min to 30 days. Auto-expiring.

Add ttl_seconds to your POST /pins body. A background sweeper unpins from Kubo when the TTL elapses; the pin record is preserved as a permanent receipt. The gateway returns 410 Gone with the receipt afterwards. Same wallet, same x402 flow.

§ 02 / The loop

Five steps. One signature.

The same x402 payment flow you know from Tack pins — with one extra field.

1

POST pin

Agent sends CID to /pins with ttl_seconds

2

402 returned

Tack returns the price (existing per-call formula)

3

Sign payment

One on-chain USDC transfer via x402

4

202 + requestid

Pin lands on Kubo; response includes expiresAt

5

Auto-expire

Sweeper unpins at TTL; gateway returns 410 with the receipt

∞ Receipt mode
Data expires. Receipt persists.

After expiry the row stays in Tack's index. GET /pins/:requestid still returns the original CID, owner, and expiredAt timestamp — a permanent record that the pin existed, paid for by the wallet on file. No extra storage. No extra payment.

§ 03 / Use cases

What your agents actually need
to pass around.

Tack Short is a fit when the data needs to be content-addressed and retrievable across a job, but doesn't justify a month of pinning.

🔁

Inter-agent handoffs

Agent A pins a task result with ttl_seconds: 1800. Agent B retrieves by CID, continues the pipeline. The data is unpinned 30 minutes later. The receipt row sticks around forever.

Typical TTL 5m–2h
⚡

Tool call caching

Expensive deterministic operations — web scrapes, API calls, slow computations — get pinned with a TTL matching your cache window. Any agent in the fleet can re-fetch by CID instead of re-executing. Auto-cleanup when stale.

Typical TTL 1h–24h
🧠

Session state snapshots

Checkpoint running agent memory mid-pipeline. Embeddings, context windows, intermediate reasoning — pinned for the lifetime of the session and unpinned when the session ends.

Typical TTL 30m–8h
📄

RAG query receipts

Not the corpus — the retrieved chunks used to generate a specific response. Pin them so any downstream system can audit exactly what context the agent had when it made a decision, then let them expire.

Typical TTL 1d–7d
🧾

Verifiable task receipts

On-chain payment, off-chain result. Pin the output, keep the wallet-signed pin record as permanent proof of delivery. The CID and the paying wallet survive after the data is unpinned.

Typical TTL 1d–30d
🔗

Inference input batches

Pass prompt batches, embedding sets, or structured API responses between pipeline steps. CIDs as pointers replace in-memory passing — decoupled, retrievable, and economically settleable.

Typical TTL 30m–4h

import { privateKeyToAccount } from "viem/accounts";
import { createPublicClient, http } from "viem";
import { taiko } from "viem/chains";

const account = privateKeyToAccount("0x...");
const signer  = toClientEvmSigner(account, createPublicClient({
  chain: taiko, transport: http()
}));

const pay = wrapFetchWithPaymentFromConfig(fetch, {
  schemes: [{ network: "eip155:167000", client: new ExactEvmScheme(signer) }]
});

// You already have a CID from /upload or your own ipfs add

const { requestid, pin, expiresAt } = await res.json();

§ 06 / Pricing

Same per-call pricing. Just shorter.

Tack Short uses the existing Tack pricing formula unchanged — TTL is an auto-cleanup primitive, not a new tier. Sub-month pricing changes can land separately once usage data shows whether agents price-shop on duration.

Pricing formula (unchanged)
price = base + max(0, ceil((sizeBytes − 1MB) / 1MB)) × perMB, capped at maxPriceUsd
Defaults: base = $0.001, perMB = $0.001, max = $0.01. Pins at or below 1 MB hit the floor regardless of TTL — which is exactly the agent-handoff sweet spot. Long pins and short pins cost the same; what TTL buys you is auto-cleanup and a permanent receipt.
§ 07 / API

Same endpoints. One new field.

Tack Short does not add new routes. It extends POST /pins with an optional ttl_seconds body field, returns expiresAt/expiredAt on the pin status response, and changes GET /ipfs/:cid to return 410 with a receipt body once the only active pin for that CID has expired.

POST /pins Create pin. Optional ttl_seconds in body. Returns 402 → sign → 202 with requestid + expiresAt x402
POST /pins/:requestid Replace pin. Same ttl_seconds field. Owner-only bearer
GET /ipfs/:cid Public retrieval. Returns 410 with { receipt: { cid, requestid, expiredAt } } once the only active pin for that CID has expired public
GET /pins/:requestid Get pin status, including expiresAt/expiredAt. Receipt is preserved after expiry bearer
GET /pins List your wallet's pins, including expired rows bearer
DEL /pins/:requestid Early-remove a pin you own. Sweeper still owns the auto-expiry path bearer
GET /.well-known/agent.json A2A agent card — advertises capabilities.pinningApi.ttl bounds and the 410 contract on the gateway public
